# Cardio Data Simulator

The Cardio Data Simulator is a Java-based application designed to simulate real-time cardiovascular data for multiple patients. This tool is particularly useful for educational purposes, enabling students to interact with real-time data streams of ECG, blood pressure, blood saturation, and other cardiovascular signals.

## Features

- Simulate real-time ECG, blood pressure, blood saturation, and blood levels data.
- Supports multiple output strategies:
  - Console output for direct observation.
  - File output for data persistence.
  - WebSocket and TCP output for networked data streaming.
- Configurable patient count and data generation rate.
- Randomized patient ID assignment for simulated data diversity.

## Getting Started

### Prerequisites

- Java JDK 11 or newer.
- Maven for managing dependencies and compiling the application.

### Installation

1. Clone the repository:

   ```sh
   git clone https://github.com/tpepels/signal_project.git
   ```

2. Navigate to the project directory:

   ```sh
   cd signal_project
   ```

3. Compile and package the application using Maven:
   ```sh
   mvn clean package
   ```
   This step compiles the source code and packages the application into an executable JAR file located in the `target/` directory.

### Running the Simulator

After packaging, you can run the simulator directly from the executable JAR:

```sh
java -jar target/cardio_generator-1.0-SNAPSHOT.jar
```

To run with specific options (e.g., to set the patient count and choose an output strategy):

```sh
java -jar target/cardio_generator-1.0-SNAPSHOT.jar --patient-count 100 --output file:./output
```

### Supported Output Options

- `console`: Directly prints the simulated data to the console.
- `file:<directory>`: Saves the simulated data to files within the specified directory.
- `websocket:<port>`: Streams the simulated data to WebSocket clients connected to the specified port.
- `tcp:<port>`: Streams the simulated data to TCP clients connected to the specified port.

1) DataAccessLayer
The Data Access Layer serves as the entry point of the Cardiovascular Health Monitoring System (CHMS). It receives raw patient data generated by the external signal generator and converts it into usable objects within the system. Each incoming datapoint represents a single measurement at a specific timestamp and is transformed into a PatientData object.

To support multiple data transmission methods, the system defines the DataListener interface. This interface specifies the core functionality required for any data source, such as startListening(), receiveData(), and stopListening(). Concrete implementations of this interface include TCPDataListener, WebSocketDataListener, and FileDataListener. Each implementation contains specific configuration attributes (such as host, port, URL, or file path) that allow it to retrieve data from the corresponding external source. This design enables the system to remain independent of the actual transmission mechanism while allowing additional data sources to be added easily in the future.
Once raw data is received, it is passed to the DataParser. The parser interprets the incoming data format (e.g., JSON or CSV) and converts it into a standardized PatientData object using the parse() method.
The resulting PatientData object is then forwarded to the DataSourceAdapter. The adapter acts as a bridge between the Data Access Layer and the internal components of the CHMS by passing the parsed datapoints to the next subsystem for further processing, such as PatientIdentificationSystem or DataStorageSystem. The PatientData class is included in the diagram because both the DataParser and DataSourceAdapter operate directly on this object.

2) PatientIdentitySystem
This system ensures that evvery incoming PatientData datapoint is correclty linked to the appropriate patient in CHMS. After the Data Access Layer converts raw input data into a PatientData object, the datapoint is passed to this subsystem for patient verification and matching.
The central component of this subsystem is the PatientIdentifier. It receives a PatientData object and extracts the patientId contained within the datapoint(it is inside the object). Using this identifier, the PatientIdentifier queries the HospitalDatabase to retrieve the corresponding HospitalPatient record. The hospital database stores official patient records, including attributes such as name, age, and a unique hospital patient ID (class: HospitalPatient).
Once a valid HospitalPatient is retrieved, the system ensures that a corresponding monitoring object exists in the CHMS. This monitoring object is represented by the Patient class, which stores the patient’s incoming health data (PatientData) and monitoring rules such as alert thresholds. The Patient object maintains a reference to its associated HospitalPatient, linking the monitoring system to the hospital’s official patient record. To explain this furthermore, the Patient object is an object for patients who are being monitored(heartrate, bloodrate, ...). Not all hospital pateints need to have this object. But every Pateint object is linked to one Hospital patient. This is also illustrated in the UML diagram.
The IdentityManager oversees the identification process and handles potential anomalies. If a patient ID cannot be matched with a hospital record, the IdentityManager manages the error through methods such as handleMismatch() or logIdentityError(). Additionally, it can create a new Patient monitoring object (class: Patient) when a valid hospital patient begins to be monitored.
Summerized, this subsystem makes sure that every incoming datapoint will be reliably added to the correct patient before being processed further

3) AlertGenerationSystem
The Alert Generation System is responsible for detecting abnormal cardiovascular measurements and generating alerts for medical staff. Once a datapoint has been successfully identified and linked to a patient, the corresponding PatientData object is evaluated within this subsystem.
The core component is the AlertGenerator, which receives incoming PatientData objects and evaluates them using the evaluate() method. Each datapoint contains a measurement value, timestamp, patient identifier, and a VitalType describing the type of vital sign being monitored. The AlertGenerator compares this measurement with the alert rules defined for the corresponding Patient.
Each patient can have multiple AlertRule objects that define personalized thresholds for specific cardiovascular conditions. These rules contain upper and lower threshold values that determine whether a measurement is within a safe range. The rules are associated with a CardiovascularIssue, which represents the specific condition being monitored, such as heart rate abnormalities or blood pressure issues. Concrete subclasses such as HeartRateIssue and BloodPressureIssue extend this abstraction to represent different cardiovascular conditions.
If the AlertGenerator detects that a measurement exceeds the configured thresholds, it creates an Alert object containing relevant information such as the patient ID, the detected cardiovascular issue, the timestamp, and a descriptive alert message.
The generated alert is then passed to the AlertManager, which is responsible for dispatching the alert to medical staff or other system components. This separation of responsibilities ensures that alert detection and alert distribution remain independent processes.
This subsystem enables real-time monitoring of patient data and ensures that critical cardiovascular anomalies are detected and communicated promptly.

4) DataStorageSystem
The Data Storage System is responsible for securely storing and retrieving patient monitoring data within the CHMS. Once a PatientData-object has passed through the previous subsystems and has been linked to a patient, it is stored as a PatientData object. Each PatientData object represents a single measurement at a specific timestamp and contains information such as the patient identifier, the type of vital sign (VitalType), the measured value, and a version number. The version attribute allows the system to maintain data versioning, which can be useful when measurements are corrected or updated.
The DataStorage class maintains a collection of patients using a map structure that associates patient identifiers with Patient objects. Each Patient object stores a list of its associated PatientData objects, allowing the system to efficiently organize monitoring data by patient.
To retrieve stored information, the system uses the DataRetrieval class. This class interacts with DataStorage and provides methods to search for patients or retrieve patient data within a specified time range.
AccessControl class controls the acces to patient data. It verifies whether a User such as a medical personnel, has teh necessary permission to access a specifc pateint's data. This makes sure, taht the medical informtion of a patient is protected.
Finally, the DataRetentionPolicy class defines how long data should be stored. It periodically removes outdated records based on a configurable retention period.
